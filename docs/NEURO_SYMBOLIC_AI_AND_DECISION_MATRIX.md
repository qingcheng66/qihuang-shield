## 一、 架构立论背景：大模型时代的“医学幻觉困境”

在人工智能大模型技术席卷各行业的背景下，医疗与中医药信息化领域面临着一个致命的行业痛点——**生成式大语言模型 (LLM) 的“概率黑盒与医学幻觉 (Medical Hallucination)”**：

1. **纯大模型方案的致命缺陷**：  
   大模型本质是基于词概率分布的生成式网络。哪怕准确率高达 98%，依然有 2% 的概率发生严重幻觉。在小说生成或日常客服中，2% 的偏差无伤大雅；但在中医药临床用药与配伍禁忌中，**一次“误把剧毒相反判定为安全”的幻觉，就可能导致肠坏死、急性心律失常乃至危及患者生命**！
2. **传统专家系统/规则库的死板瓶颈**：  
   传统的纯规则库虽然“绝对确定、永不幻觉”，但面对复杂多变的现实世界极其脆弱——遇到手写处方 OCR 错字（如把“白术”识为“白木”）、古代度量衡混用（如“一钱”、“两分”）、或者需要深入阐述“为什么相反、君臣佐使如何配合”时，传统代码无法理解与推演，沦为枯燥死板的静态字典。

为破解这一根本矛盾，《岐黄盾》在业内率先提出了**“感知纠偏靠神经网络，生命红线归符号规则，深度方解赋能大模型”**的**神经-符号双脑协同机制 (Neuro-Symbolic Architecture)**。

## 三、 AI 任务决策率与权责分层定量矩阵

在平台全流程中，AI 模型的决策权与影响率根据任务对生命安全的敏感度，进行了精确的**权重分级控制**：

| 业务任务阶段 | 主导技术引擎 | 辅助技术引擎 | **AI 对最终结果的影响率** | 权责分配与安全边界设计 |
| :--- | :--- | :--- | :---: | :--- |
| **1. 终极安全红线裁决**<br/>(十八反、十九畏、极量超标) | **Java 纯内存规则引擎**<br/>(Set 碰撞算法) | 无（AI 仅作为输入提取源） | **0% ~ 10%**<br/>(AI 绝无最终裁判权) | **生命安全底线一票否决！** 无论 AI 大模型说什么，只要命中了 Java 规则字典，系统强制亮起红灯并阻断处方，杜绝一切医学幻觉误报。 |
| **2. 字符感知与视觉提取**<br/>(处方字符 OCR、舌象特征) | **PaddleOCR + OpenCV**<br/>(轻量深度学习模型) | 正则词性校验 | **85% ~ 90%**<br/>(AI 占绝对感知主导) | 决定了原始图像能否被正确读取与数字化。纯本地运行，保证数据隐私不泄露。 |
| **3. 错字纠偏与实体规范化**<br/>(古度量衡换算、错别字修正) | **大语言模型 (LLM)**<br/>(通义千问 / DeepSeek) | 常用中药字典白名单 | **80% ~ 85%**<br/>(AI 占语义理解主导) | 将非结构化文字清洗为标准化中药名与剂量。大幅提升系统在真实潦草手写处方下的鲁棒性。 |
| **4. 深度方解与古籍病机推演**<br/>(君臣佐使剖析、替代方案) | **RAG 向量库 + LLM**<br/>(知识增强大模型) | 静态古籍注释模板 | **85% ~ 90%**<br/>(AI 决定价值感知) | 决定了系统是“死板的数据库查表”，还是“资深名医级综合研判”。评委主观评分的关键赋能点。 |
| **5. 数字舌象与九维体质判定**<br/>(舌色聚类、苔质比率) | **OpenCV 机器视觉模型**<br/>(CIELAB / HSV) | 中医体质积分算法 | **90% ~ 100%**<br/>(AI 全权量化主导) | 舌质颜色 LAB 与苔质面积占比完全由机器视觉模型计算得出，消除人工肉眼主观误差。 |

### 2. 硬件可行性测算与为什么“严禁跑本地大模型”？
* **内存测算推演**：  
  如果试图在 2 核 4G 机器上部署本地轻量 7B 大模型（即使经过 4-bit 量化），模型权重常驻内存即需 **4.5 GB**，会瞬间撑爆 3.6 GB 可用内存，导致 Linux 系统触发 OOM Killer 强制杀死进程；且 2 核 CPU 缺乏 AVX-512 与 GPU 算力，推理速度低于 1 Token/秒，在演示现场极易假死。
* **微服务全栈上云 + 云端 LLM API 的最佳工程解**：  
  我们的异构微服务经过极致内存优化，常驻内存分布如下：

| 进程组件 | 优化运行参数 | 内存占用 | 运行状态 |
| :--- | :--- | :---: | :---: |
| **Nginx Web 服务** | 静态托管前端 Vue 3 构建产物 | **~ 20 MB** | 极轻极快 |
| **Java 业务与规则中枢** | `-Xms256m -Xmx512m` (Spring Boot 3 + JDK 21) | **~ 380 MB** | 毫秒级稳定常驻 |
| **Python 计算节点** | FastAPI + RapidOCR (PaddleOCR ONNX CPU) | **~ 350 MB** | 纯 CPU 本地推理 |
| **RAG 向量与古籍检索** | 纯 Python 内存向量索引 + BM25 语料切片 | **~ 50 MB** | 检索耗时 < 5ms |
| **Ubuntu 系统底座** | 系统核心常驻进程 | **~ 400 MB** | 稳定运行 |
| **【微服务整机总内存】** | —— | **约 1.2 GB** | **剩余 2.4 GB 充裕安全缓冲！** |

> **论证结论**：将 Java 业务中枢、Python OCR/视觉计算节点与 RAG 检索部署在腾讯云 2 核 4G 服务器上，**内存占用率仅约 33%**，完全不会发生内存抖动；而推理生成调用 **DeepSeek / 通义千问云端 API**，实现“0 本地算力开销、1~2 秒内极速推演”的工业级高可用架构。
